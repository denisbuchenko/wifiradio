# Architecture

## Native desktop app

The application uses Rust and Win32 directly through `windows-sys` 0.59. There is no browser, WebView, server, installer, or external runtime. `ui.rs` owns the main window, two accessible owner-drawn native buttons, and the notification icon. `WindowContext` separates an always-accessible command sender from the `RefCell<App>` guarding mutable UI state. Window destruction sends Shutdown, removes the tray icon, and posts WM_QUIT without borrowing App. This matters when a native popup or message box already holds that borrow: older versions could destroy the window but skip shutdown and leave a windowless process alive. The UI polls an engine snapshot every 60 ms and sends Begin/End/SetPeer/Shutdown commands to its worker. Network counters do not cause tray icon replacement or main-window repainting.

`connection.rs` provides the optional modeless Connection window under the overflow menu. It shows physical LAN IPs, an optional peer IPv4 field, packet counters, and the last network error. `Rc<RefCell<Dialog>>` keeps state alive across nested Windows messages and destruction of the owner. Empty input restores automatic discovery. A manual address must be another host on a selected on-link subnet. It is stored beside the executable in `wifiradio.peer`. This window does not block the engine or main window.

The push-to-talk button handles pointer capture, space key transitions, focus loss, and cancellation. X and Exit fully close the application. Minimize and Escape retain the taskbar window. Only the explicit Hide to Tray action hides it, after Shell confirms the icon is registered; a failed icon registration leaves the window reachable. Startup with `--background` also falls back to a visible window when the tray is unavailable. The tray icon is restored after an Explorer restart using `TaskbarCreated`, with add/modify retry paths. Explicit open calls consume Windows' first-ShowWindow STARTUPINFO override before forcing SW_RESTORE, so a hidden launcher cannot swallow the open request.

`instance.rs` owns a per-session mutex (`v3`) and captures `GetLastError` immediately after creating it. A second launch checks the existing UI's version and requires a synchronous, timed activation acknowledgement, including during nested menus/dialogs. A second launch with `--background` still restores an already running app. Legacy or unresponsive windows are closed and replaced. Recovery verifies the process image filename belongs to WifiRadio; an unresponsive matching process may be terminated after a two-second graceful timeout. No unrelated executable is terminated.

After obtaining the startup lock, the launcher also checks Windows' UDP owner table for port 49735. A windowless legacy radio holding that port is recoverable by its verified WifiRadio process image. An unrelated port owner is left alone and produces a visible bind error. The owned mutex is released on normal exit and can be acquired after abandonment. Missing windows, activation failures, and native startup errors are never silently discarded. `logging.rs` keeps a small rotating local log beside the executable without voice, packet contents, or pairing keys. Panic reports also go there. Shutdown waits at most 800 ms for the audio/network worker; process exit releases Windows handles if a driver stalls.

`startup.rs` adds a current-user Run value on first real launch. A marker beside the executable prevents re-enabling startup after the user disables it. An enabled entry is updated to the current executable path, supporting versioned filenames without reviving old builds at sign-in. Tests and test-initiated restarts use `--no-autostart` and never edit this value.

## LAN transport

`engine.rs` binds UDP 49735 and sends an encrypted Hello once per second to the selected LANs' directed broadcast addresses. `network.rs` uses Windows `GetIfEntry2` to prefer active hardware interfaces over TAP/TUN/WireGuard adapters, independent of VPN product names. If no hardware adapter has an eligible IPv4 address, virtual LAN interfaces remain usable. The broadcast is calculated from the address and `OnLinkPrefixLength`; `if-addrs` 0.13 on Windows may derive its separate broadcast/netmask fields from a host /32 prefix instead.

Before each destination change, the outgoing socket is bound to the matching interface with Winsock `IP_UNICAST_IF`, whose interface index must be in network byte order. Packets outside selected on-link subnets are not sent through the VPN/default route. Loopback remains available for local verification. Adapter addresses refresh every ten seconds so Wi-Fi changes recover without restarting. IP TTL is one.

While disconnected, a fallback sends one encrypted unicast Hello every 25 ms to hosts in the local /24-sized block per adapter (or its smaller actual subnet). It excludes own, network, and broadcast addresses. A typical /24 pass takes about seven seconds. It sends only this app's authenticated presence message to UDP 49735, without ICMP/TCP scanning or visiting other blocks of a large LAN. Discovery probes stop while connected. A manual peer address disables broadcast and fallback searches and receives a unicast Hello once per second; authenticated packets from other IPs are ignored. Keepalives, handshakes, and voice use the same explicit interface routing.

A peer expires after five seconds. Bye removes it immediately on a graceful exit. The first authenticated peer is selected in automatic mode; this version is designed for two PCs. Changing connection mode sends Bye, stops capture, and restarts discovery. VPN kill switches and Windows Filtering Platform rules can still block LAN packets; the app never changes those policies or firewall rules.

`protocol.rs` uses XChaCha20-Poly1305 with a random 256-bit build key. `build.rs` creates the ignored `.local/room.key` once and copies it to `OUT_DIR` for embedding. A random 128-bit process identity plus a monotonically increasing 64-bit packet counter form a unique 192-bit nonce. The protocol version `WR01` is authenticated additional data. Packet lengths and message types are validated before use. The selected peer has a 128-packet replay window, allowing bounded UDP reordering and rejecting duplicates. Restarting produces a new identity.

Messages: Hello, Bye, Start(talk id, warning flag), Ready(talk id, warning flag), Audio(talk id, frame sequence, PCM), End(talk id). Start retries every 100 ms for up to four seconds. Receivers acknowledge repeated starts without repeating the warning. End is sent three times. Stale utterance starts and audio are ignored. If both users press together, the lexicographically smaller node identity wins. Both sides support half-duplex audio.

## Audio and warning

`audio.rs` wraps the built-in WinMM waveform API. Audio is mono 16 kHz, signed 16-bit PCM, in 20 ms/640-byte frames. An audio datagram is 697 bytes including protocol fields, nonce, and authentication tag. Raw PCM is approximately 256 kbit/s before network overhead. This is suitable for a home LAN and needs no codec DLL.

The capture handle is created on press but recording starts only after the handshake. It is reset, unprepared, and closed on release. Boxed, explicitly aligned driver headers and boxed PCM buffers stay at stable addresses until Windows returns them. The speaker uses a bounded queue. Warning gates wait for both the nominal interval and the actual driver buffer completion, so a slow output device does not cause early recording. A 60 ms receive jitter buffer reorders frames, fills lost frames with silence, discards late frames, and bounds catch-up latency. No audio goes to disk.

`Activity` tracks actual outgoing and incoming frames rather than presence or button taps. The first conversation and any conversation after 180 seconds without frames trigger three 110 ms sine tones, each followed by 50 ms silence: C5/E5/G5, with short fades and 12% sample amplitude. The total is 480 ms. The sender plays its tones immediately; the receiver plays its own tones when Start arrives, then sends Ready after the warning interval. The sender starts capture only when it has Ready and its own interval has elapsed. A restarted receiver can request a warning through Ready, in which case the sender also warns before capture. A lost handshake fails closed.

## Scope

Windows 10/11 x64, two PCs on the same IPv4 LAN, default Windows input/output devices. No NAT traversal, recording, global hotkey, conferencing, or device selector. Network isolation on a guest SSID and firewall policy can prevent LAN discovery. Hardware sound and real Wi-Fi delivery require checks on the target PCs in addition to loopback tests.
